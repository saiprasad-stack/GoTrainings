# Database Handling in Go – Comparison

| Approach | What it is | How it works | Where queries are written | Step-by-step flow | Pros | Cons | Production usage | When to use |
|----------|-----------|-------------|--------------------------|------------------|------|------|------------------|-------------|
| **database/sql (Raw SQL)** | Standard Go DB package with drivers | You manually write SQL and execute it using Go functions | Inside Go code (SQL strings in files like repository layer) | 1. Call function → 2. SQL string prepared → 3. Sent via driver → 4. DB executes → 5. Rows returned → 6. Manual scan into struct | Full control, predictable performance, no abstraction overhead | Boilerplate code, manual mapping, hard to maintain at scale | Yes (very common, especially in controlled systems) | Small to medium apps, performance-critical systems |
| **Query Builders** | Libraries to construct SQL programmatically | Build SQL using functions instead of raw strings | Inside Go code (structured builder syntax) | 1. Build query object → 2. Convert to SQL → 3. Execute via driver → 4. Scan result manually | Safer query building, good for dynamic queries, reduces syntax errors | Harder debugging, still manual mapping, not fully type-safe | Yes (used in dynamic query-heavy systems) | Systems with complex filters/search queries |
| **ORM (GORM, Ent, Bun)** | Maps Go structs to DB tables | You define structs and call ORM methods; SQL auto-generated | Not written explicitly (hidden inside ORM) | 1. Call ORM method → 2. ORM generates SQL → 3. Query sent → 4. DB executes → 5. ORM maps result to struct | Fast development, minimal SQL, easy CRUD | Hidden queries, performance issues, less control, debugging complexity | Yes (especially startups, CRUD-heavy apps) | Rapid development, simple applications |
| **Code Generation (sqlc, xo)** | SQL-first approach with generated Go code | Write SQL in files → tool generates type-safe Go methods | Separate `.sql` files (best practice) | 1. Write SQL → 2. Run generator → 3. Call generated function → 4. Executes SQL → 5. Returns typed result | Type-safe, explicit SQL, no runtime overhead, clean separation | Setup required, regeneration needed on changes | Highly recommended (modern production systems) | Medium to large production systems |
| **Native Drivers (pgx, etc.)** | Direct DB drivers without abstraction | Interact directly with DB protocol using driver APIs | Inside Go code OR `.sql` (if combined with sqlc) | 1. Call driver method → 2. SQL sent directly → 3. DB executes → 4. Result returned → 5. Manual or generated mapping | High performance, advanced features (batching, streaming) | More complex, less abstraction | Yes (high-performance systems) | Microservices, high-throughput systems |
| **NoSQL (MongoDB, Redis)** | Non-relational database access | Use client libraries with object-based queries | Inside Go code (structured query objects, not SQL) | 1. Build query object → 2. Send to DB → 3. DB executes → 4. Returns JSON-like data → 5. Map to struct | Flexible schema, scalable, good for caching and distributed systems | No joins, data duplication, different modeling approach | Yes (specific use cases like caching, logs, analytics) | When relational DB is not suitable |
